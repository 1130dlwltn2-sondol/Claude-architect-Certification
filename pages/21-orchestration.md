# 21. 오케스트레이션 패턴과 Agent SDK

20장에서 5가지 패턴의 지도를 그렸다면, 이번 장에서는 시험에서 가장 깊이 물어보는 오케스트레이션 영역으로 들어갑니다. 여러 개의 에이전트를 엮어 하나의 일을 시키는 방법입니다.

## Coordinator-Subagent 패턴

공식 시험 안내에서 직접 언급하는 패턴입니다. 코디네이터(coordinator)가 전체 작업을 이해하고, 서브에이전트(subagent)들에게 일을 나눠주고, 결과를 모읍니다.

서브에이전트를 쓰는 이유는 컨텍스트 분리입니다. 하나의 에이전트가 모든 일을 하면 컨텍스트 윈도우가 금방 찹니다. 서브에이전트는 각자 자신의 컨텍스트를 가지고 일하고, 코디네이터에게는 결과만 보고합니다. 코디네이터의 컨텍스트는 깨끗하게 유지됩니다.

예시: 코드베이스 리팩터링. 코디네이터가 "결제 모듈의 에러 처리를 표준화하라"는 지시를 받으면, 서브에이전트 A에게 결제 모듈 파일 목록 조사를, B에게 에러 처리 패턴 분석을, C에게 테스트 코드 작성을 맡깁니다. 각 서브에이전트는 자기 작업의 결과만 돌려주고, 코디네이터가 최종 패치를 만듭니다.

설계 시 결정할 것들:

- 분해 기준: 파일 단위, 기능 단위, 단계 단위 중 무엇으로 나눌 것인가
- 통신 방식: 서브에이전트끼리 직접 대화하게 할 것인가, 코디네이터를 통해서만 하게 할 것인가
- 종합 방법: 결과를 단순히 이어 붙일 것인가, 코디네이터가 다시 검증할 것인가

## 작업 분해 (Task decomposition)

복잡한 작업을 다루는 첫 단계는 나누기입니다. 분해에는 두 가지 방식이 있습니다.

정적 분해: 사람이 미리 나눕니다. "1단계 수집, 2단계 분석, 3단계 보고서 작성"처럼 순서가 정해져 있을 때 씁니다. 예측 가능하고 디버깅이 쉽습니다.

동적 분해: 모델이 실행 중에 나눕니다. 오케스트레이터-워커 패턴이 여기에 해당합니다. 유연하지만, 어디서 일이 꼬였는지 추적하기 어렵습니다.

시험에서는 "이 상황에서 정적 분해와 동적 분해 중 무엇이 적절한가"를 묻습니다. 판단 기준은 예측 가능성입니다. 하위 작업을 미리 알 수 있으면 정적으로, 없으면 동적으로 나눕니다.

## 세션 상태 관리

여러 단계에 걸친 작업에서는 상태를 어딘가에 들고 있어야 합니다. 시험 안내에서 "세션 상태와 워크플로우 강제"를 명시한 이유입니다.

상태를 관리하는 방법:

- 대화 기록에 누적: 가장 단순하지만 컨텍스트를 빠르게 소모합니다
- 외부 저장소: 작업 상태를 DB나 파일에 저장하고, 필요할 때만 읽어옵니다
- 요약: 긴 기록을 주기적으로 요약해 다음 단계로 넘깁니다

워크플로우 강제(workflow enforcement)란, 정해진 순서를 모델이 건너뛰지 못하게 하는 장치입니다. 예를 들어 "분석을 하기 전에 반드시 데이터를 조회하라"는 규칙을 코드로 강제합니다. 모델에게 맡기는 부분과 코드로 고정하는 부분을 나누는 감각이 중요합니다.

## Claude Agent SDK

직접 API를 호출해 에이전트 루프를 만들 수도 있지만, 정형화된 작업에는 SDK가 편합니다. Claude Agent SDK는 LLM 호출, 도구 정의와 파싱, 호출 체이닝 같은 반복 작업을 단순화합니다.

다만 Anthropic의 조언을 기억하세요. 프레임워크는 추상화 계층을 추가하고, 그 밑에서 무슨 일이 일어나는지 가립니다. SDK를 쓰더라도 내부 동작을 이해하고 있어야 디버깅이 됩니다. 시험에서도 "SDK를 쓰면 좋은 경우와 직접 구현이 나은 경우"를 구분하는 문제가 나옵니다.

SDK가 유리한 경우: 표준적인 에이전트 루프, 도구 호출, 세션 관리가 필요한 경우
직접 구현이 나은 경우: 특수한 제어 흐름, 커스텀 정지 조건, 세밀한 컨텍스트 제어가 필요한 경우

## 예제: 간단한 에이전트 루프

```python
import anthropic

client = anthropic.Anthropic()
MAX_STEPS = 10

def run_agent(user_request, tools):
    messages = [{"role": "user", "content": user_request}]
    for step in range(MAX_STEPS):
        response = client.messages.create(
            model="claude-sonnet-4-5-20250929",
            max_tokens=1024,
            tools=tools,
            messages=messages,
        )
        messages.append({"role": "assistant", "content": response.content})
        tool_uses = [b for b in response.content if b.type == "tool_use"]
        if not tool_uses:
            return response  # 도구 호출이 없으면 완료
        results = [execute_tool(t) for t in tool_uses]
        messages.append({"role": "user", "content": results})
    raise RuntimeError("최대 반복 횟수 초과")
```

이 코드에서 시험 포인트는 세 가지입니다. 정지 조건(MAX_STEPS), 도구 실행 결과의 피드백, 그리고 메시지 누적에 따른 컨텍스트 증가입니다.

## 실습: 서브에이전트 분해 설계

"우리 팀의 주간 보고서를 자동으로 만드는 시스템"을 가정하고, 코디네이터-서브에이전트 구조를 종이에 설계해 봅니다.

1. 코디네이터의 역할을 한 문장으로 정의
2. 서브에이전트 3개를 정하고 각각의 입력과 출력을 명시
3. 서브에이전트끼리 정보를 공유해야 하는 지점이 있는지 표시
4. 전체 작업의 정지 조건 정의

코드로 구현하지 않아도 됩니다. 분해와 인터페이스를 종이에 그리는 것만으로 오케스트레이션 감각이 생깁니다.
