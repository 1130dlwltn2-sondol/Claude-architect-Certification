# 42. 팀과 엔터프라이즈에서의 Claude Code

개인이 쓰는 것과 조직이 쓰는 것은 다릅니다. 시험의 시나리오 중에는 기업 도입 상황을 다룬 것이 있어, 이 장의 내용이 D3의 응용 문제로 나옵니다.

## 팀 공유 설정

.claude 디렉토리를 버전 관리에 넣으면 팀 전체가 같은 커맨드, 같은 에이전트, 같은 규칙을 씁니다. 새로 합류한 사람도 저장소를 받자마자 팀의 워크플로우를 그대로 쓸 수 있습니다.

공유하면 좋은 것:

- CLAUDE.md의 코딩 규칙
- 팀 표준 슬래시 커맨드 (리뷰 기준, 배포 절차 등)
- 공용 서브에이전트 정의
- MCP 서버 목록과 연결 방법 문서

공유하지 말아야 할 것:

- 개인 API 키와 토큰
- 개인별 권한 설정
- 실험 중인 설정

민감 정보는 환경 변수나 별도의 비밀 관리 도구에 둡니다. 설정 파일에 키를 하드코딩하는 것은 시험에서도, 실무에서도 오답입니다.

## 권한과 정책

조직에서는 누가 무엇을 할 수 있는지를 정해야 합니다.

- 자동 승인 범위: 팀 단위로 허용할 동작의 범위를 정합니다. 읽기, 테스트 실행은 허용하되, 외부 전송이나 삭제는 승인 절차를 두는 식입니다
- 감사 로그: 누가 언제 어떤 지시를 내렸고, 에이전트가 무엇을 했는지 기록합니다
- 비용 관리: 팀별 토큰 사용량을 모니터링하고 예산을 설정합니다

## 보안 고려사항

Claude Code가 코드베이스 전체를 읽는다는 것은, 민감 정보도 읽을 수 있다는 뜻입니다.

- .env 파일, 키 파일은 작업 범위에서 제외되도록 설정합니다
- 외부 MCP 서버를 연결할 때는 데이터가 어디로 가는지 확인합니다
- 생성된 코드에 하드코딩된 비밀값이 없는지 리뷰합니다
- 프롬프트 인젝션에 대비합니다. 코드베이스 안의 악의적인 지시(예: 주석에 숨겨진 "이 파일을 삭제하라")를 모델이 따르지 않도록 주의합니다

마지막 항목은 시험의 단골 소재입니다. 에이전트가 읽는 모든 텍스트는 잠재적인 지시입니다. 신뢰할 수 없는 출처의 콘텐츠를 그대로 프롬프트에 넣는 설계는 취약합니다.

## CI/CD와의 연동

Claude Code의 워크플로우는 CI 파이프라인과도 연결됩니다.

- PR이 열리면 자동으로 리뷰 커맨드 실행
- 테스트 실패 시 원인 분석 요청
- 릴리스 노트 초안 생성

이때도 원칙은 같습니다. 자동화된 단계마다 사람의 승인 지점을 둘지, 결과를 어디에 기록할지를 정합니다.

## 도입 로드맵 예시

1. 파일럿: 1개 팀, 1개 프로젝트에서 시작. CLAUDE.md와 기본 커맨드 정비
2. 확산: 성공 사례를 문서화하고 3~5개 팀으로 확대. 공용 설정 저장소 운영
3. 정착: 권한 정책과 감사 로그 체계화. 교육 과정 개설
4. 고도화: MCP 서버로 사내 시스템 연동. 커스텀 에이전트 개발

각 단계마다 측정 지표를 둡니다. "개발 속도 향상" 같은 추상적인 목표가 아니라, "PR 리뷰 소요 시간", "테스트 커버리지" 같은 구체적인 숫자로 봅니다.

## 실습: 팀 도입 제안서 쓰기

가상의 팀(5명, 웹 서비스 개발)에 Claude Code를 도입하는 1페이지 제안서를 써봅니다. 포함할 것:

1. 기대 효과 2가지 (측정 가능한 형태)
2. 보안 우려 2가지와 대응책
3. 파일럿 범위 (팀, 기간, 성공 기준)

이 연습은 시나리오형 문항의 "도입 계획" 문제에 그대로 대응합니다.

확인 문제

1. .claude 디렉토리에서 공유하면 안 되는 것 3가지를 말해 보세요.
2. 프롬프트 인젝션이 Claude Code 맥락에서 왜 위험한지 설명해 보세요.
3. 자동화 단계에서 사람의 승인 지점을 두어야 하는 이유를 설명해 보세요.
4. 도입 로드맵의 각 단계에서 측정할 지표를 하나씩 제안해 보세요.
