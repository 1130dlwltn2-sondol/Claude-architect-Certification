# 62. 신뢰성과 운영 안정성

컨텍스트를 잘 다뤄도, 운영에서 모델은 실패합니다. API 오류, 잘못된 출력, 예상 밖의 입력이 일어납니다. D5의 나머지 절반은 이런 실패에 대비하는 신뢰성 설계입니다.

## 재시도와 폴백

API 호출이 실패하면 다시 시도합니다. 다만 무작정 반복하면 안 됩니다.

재시도 전략:

- 지수 백오프: 실패할 때마다 대기 시간을 늘립니다 (1초, 2초, 4초...)
- 최대 횟수: 3~5회 후에는 포기합니다
- 재시도 가능한 오류만: 일시적 오류(429, 5xx)는 재시도하고, 잘못된 요청(400)은 바로 중단합니다

폴백(fallback)은 재시도로도 안 될 때의 차선책입니다.

- 큰 모델이 안 되면 작은 모델로
- 실시간 처리가 안 되면 큐에 쌓아두고 나중에
- AI 답변이 안 나오면 기본 답변이나 사람에게 전달

"실패했을 때 사용자는 무엇을 보는가"를 미리 정하는 것이 신뢰성의 핵심입니다.

## 타임아웃과 데드라인

각 단계에 시간 제한을 둡니다. 한 단계가 붙잡고 있으면 전체가 멈춥니다.

- API 호출 타임아웃: 보통 30~60초
- 전체 작업 데드라인: 에이전트 루프의 시간 제한 (22장)
- 단계별 예산: "검색은 10초以内" 같은 세부 제한

## 출력 검증

모델의 출력이 형식을 지키는지 코드로 검증합니다.

```python
import json

def parse_or_retry(raw, max_attempts=3):
    for _ in range(max_attempts):
        try:
            data = json.loads(raw)
            validate_schema(data)  # 스키마 검사
            return data
        except (json.JSONDecodeError, ValueError):
            raw = ask_again_with_correction(raw)
    return fallback_response()
```

구조화 출력(51장)을 써도 검증은 필요합니다. "거의 맞는" JSON이 나올 때가 있기 때문입니다.

## 모니터링

운영 중인 시스템은 봐야 합니다.

- 호출량과 토큰 사용량: 비용 추적
- 지연 시간: 단계별 소요 시간
- 오류율: 재시도, 폴백 발생 빈도
- 품질 지표: 사용자 만족도, 작업 성공률

이상 징후의 예: 특정 시간대에 오류율이 올라가면 API 상태 문제일 수 있고, 특정 유형의 질문에서 실패가 많으면 프롬프트나 RAG의 문제일 수 있습니다.

## 비용 가드레일

토큰 비용이 폭주하지 않게 상한을 둡니다.

- 일일/월별 예산 설정과 알림
- 작업당 토큰 상한 (초과 시 중단)
- 비정상 패턴 탐지 (갑작스러운 사용량 급증)

22장의 정지 조건 중 "비용 상한"과 같은 맥락입니다.

## 변경 관리

프롬프트나 모델을 바꾸면 평가부터 다시 합니다(22장). 운영 중인 시스템의 변경 원칙:

1. 스테이징 환경에서 먼저 테스트
2. 소량 트래픽으로 카나리 배포
3. 지표 비교 후 전체 적용
4. 문제 발생 시 즉시 롤백

프롬프트 변경도 코드 변경과 같은 절차를 따릅니다. 버전 관리에 프롬프트를 포함시키는 것이 좋습니다.

## 장애 대응 플레이북

자주 일어나는 장애와 대응을 미리 정리합니다.

| 장애 | 증상 | 대응 |
|---|---|---|
| API 일시 오류 | 5xx, 타임아웃 | 지수 백오프 재시도 |
| 할당량 초과 | 429 | 요청 분산, 작은 모델 폴백 |
| 형식 오류 | 파싱 실패 | 재요청 후 폴백 |
| 품질 저하 | 사용자 불만 증가 | 프롬프트 롤백, 평가 재실행 |
| 비용 폭증 | 사용량 급증 | 상한 발동, 원인 분석 |
