# 50. 프롬프트 엔지니어링 기초

Part 5에서는 시험 비중 20%의 Domain 4를 다룹니다. 프롬프트 엔지니어링은 가장 익숙한 주제이지만, 시험은 "왜 이렇게 쓰는가"의 원리를 묻습니다.

## 명확하게 쓰기

모호한 지시는 모호한 답을 낳습니다. 프롬프트 작성의 첫 원칙은 구체성입니다.

모호한 예: "이 코드를 개선해줘"
구체적인 예: "이 함수의 시간 복잡도를 O(n)으로 개선해줘. 외부 라이브러리는 추가하지 말고, 기존 테스트가 모두 통과해야 해."

구체적으로 적을 것들:

- 원하는 결과물의 형태 (표, 코드, 불릿 리스트 등)
- 지켜야 할 제약 (길이, 스타일, 금지 사항)
- 판단 기준 (무엇을 우선할지)

## 컨텍스트 주기

모델은 주어진 것만 압니다. 배경 정보를 충분히 주세요.

- 이 작업의 목적이 무엇인지
- 누가, 어디에 쓸 것인지
- 관련 제약이나 전제 조건

예: "우리 팀의 주간 회의용 자료야. 참석자는 비개발 직군이라 기술 용어는 풀어서 설명해줘." 한 문장의 배경이 답의 톤을 바꿉니다.

## 예시 보여주기 (Few-shot)

원하는 형식이 있으면 말로 설명하지 말고 예시를 보여주세요.

```
입력: "배송이 너무 느려요"
출력: {"감정": "부정", "주제": "배송"}

입력: "포장이 예뻐서 기분 좋았어요"
출력: {"감정": "긍정", "주제": "포장"}

입력: "사이즈가 생각보다 작네요"
출력:
```

예시를 2~3개 주면 모델은 패턴을 파악합니다. 형식이 복잡할수록 예시의 효과가 큽니다. 다만 예시가 너무 많으면 컨텍스트를 잡아먹으니 균형을 맞추세요.

## 역할 부여

"당신은 시니어 백엔드 개발자입니다" 같은 역할 지정은 답의 관점을 맞춥니다. 만능은 아니지만, 톤과 깊이를 조정하는 데 유용합니다. 특히 리뷰나 자문 상황에서 효과적입니다.

## 단계적으로 생각하게 하기

복잡한 문제에는 "단계별로 생각해 보세요"라는 한 문장이 도움이 됩니다. 모델이 중간 추론 과정을 거치면 정확도가 올라갑니다. 다만 추론 과정이 길어지면 토큰 비용이 늘고, 최종 답에 불필요한 과정이 섞일 수 있습니다. 구조화 출력(51장)과 함께 쓰면 과정과 결과를 분리할 수 있습니다.

## 형식 지정

원하는 출력 형식을 명시합니다.

- "표로 정리해줘"
- "JSON으로 출력해줘. 키는 name, price, stock으로 해줘"
- "3줄 이내로 요약해줘"

형식을 정하면 후처리가 쉬워집니다. 파이프라인의 다음 단계가 코드라면, 형식 지정은 필수입니다.

## 예제: 나쁜 프롬프트 고치기

변경 전:
"회의록 정리해줘"

변경 후:
"아래 회의 녹취록을 정리해줘. 출력 형식: 1) 결정 사항 (불릿 5개 이내), 2) 액션 아이템 (담당자와 기한 포함, 표 형식), 3) 미결 사항. 기술 용어는 그대로 두고, 발언자의 말버릇은 제거해줘."

무엇이 달라졌나요. 출력 구조, 각 섹션의 형식, 처리 기준이 명시되었습니다.

## 실습: 프롬프트 개선 실험

같은 작업에 대해 프롬프트 3단계를 만들어 결과를 비교합니다.

1. 한 문장짜리 모호한 프롬프트
2. 구체적인 지시와 형식을 담은 프롬프트
3. 배경 정보와 예시를 추가한 프롬프트

각 결과를 보고 무엇이 달라졌는지 기록합니다. 이 경험이 "어떤 기법을 언제 쓰는가"라는 시험 문제의 답이 됩니다.

확인 문제

1. 구체적인 프롬프트에 들어가야 할 3가지 요소를 말해 보세요.
2. few-shot이 특히 효과적인 경우를 설명해 보세요.
3. 단계적 사고 유도의 장점과 단점을 말해 보세요.
4. 위 예제에서 "말버릇 제거" 같은 처리 기준을 명시하는 이유를 설명해 보세요.
