# 30. 도구 설계의 원칙

에이전트의 성능은 도구의 품질에서 갈립니다. Anthropic의 표현을 빌리면, 에이전트와 컴퓨터 사이의 인터페이스(ACI, agent-computer interface)를 정성껏 만드는 것이 핵심입니다. 이 장에서는 시험 비중 18%의 Domain 2 중 도구 설계 부분을 다룹니다.

## 도구란 무엇인가

도구는 모델이 호출할 수 있는 함수입니다. 모델은 도구를 직접 실행하지 않습니다. "이 함수를 이런 인자로 호출하고 싶다"는 요청을 내보내고, 실제 실행은 우리 코드가 합니다. 실행 결과를 다시 모델에게 주면, 모델은 다음 행동을 결정합니다.

도구 정의는 보통 세 부분으로 이루어집니다.

- 이름(name): 모델이 부를 이름
- 설명(description): 언제, 왜 쓰는지를 설명하는 문장
- 파라미터(parameter): JSON Schema로 정의한 입력 형식

## 좋은 이름과 설명

모델은 설명을 읽고 도구를 고릅니다. 설명이 모호하면 선택도 모호해집니다.

나쁜 예: "데이터를 가져옵니다"
좋은 예: "주어진 기간의 일별 매출 합계를 조회합니다. 기간은 YYYY-MM-DD 형식의 시작일과 종료일로 지정합니다. 90일을 초과할 수 없습니다."

좋은 설명의 조건:

1. 무엇을 하는지가 한 문장으로 명확하다
2. 언제 써야 하는지가 드러난다 ("~할 때 사용하세요")
3. 언제 쓰지 말아야 하는지도 적혀 있다 ("~는 다른 도구를 쓰세요")
4. 인자의 형식과 제약이 명시되어 있다

이름도 마찬가지입니다. get_data 같은 이름보다 get_daily_sales 같은 이름이 모델의 선택을 돕습니다. 이름에 동사와 대상을 분명히 넣으세요.

## JSON Schema로 파라미터 정의하기

파라미터는 JSON Schema로 정의합니다. 모델이 이 스키마를 보고 인자를 만듭니다.

```python
{
    "name": "get_daily_sales",
    "description": "주어진 기간의 일별 매출 합계를 조회합니다. 리포트 작성 시 사용하세요. 실시간 재고 조회에는 쓰지 마세요.",
    "input_schema": {
        "type": "object",
        "properties": {
            "start_date": {
                "type": "string",
                "description": "조회 시작일 (YYYY-MM-DD)",
            },
            "end_date": {
                "type": "string",
                "description": "조회 종료일 (YYYY-MM-DD). 시작일로부터 90일 이내여야 합니다."
            },
        },
        "required": ["start_date", "end_date"],
    },
}
```

스키마 작성 요령:

- required를 명시해 필수 인자를 분명히 합니다
- 각 필드에 description을 달아 형식과 제약을 적습니다
- enum으로 허용 값을 제한하면 모델의 실수가 줄어듭니다
- 중첩이 깊어지면 모델이 헷갈립니다. 2단계 이내로 유지하세요

## 도구를 얼마나 잘게 나눌 것인가

너무 잘게 나누면: 모델이 여러 번 호출해야 해서 느리고 비싸집니다. 중간에 하나라도 실패하면 전체가 꼬입니다.

너무 크게 묶으면: 하나의 도구가 여러 일을 해서 설명이 모호해집니다. 모델이 필요한 부분만 쓰기 어렵습니다.

기준은 "하나의 명확한 목적"입니다. "매출 조회"는 하나의 도구, "매출 조회 후 보고서 작성"은 두 개의 일입니다. 시험에서는 "이 도구 설계의 문제점은?" 같은 문항으로 나옵니다. 쪼개야 할 것을 뭉쳐놓은 보기를 찾으면 됩니다.

## 에러 처리와 피드백

도구가 실패했을 때 돌려주는 메시지도 설계 대상입니다. 모델이 다음 행동을 정하는 근거가 되기 때문입니다.

나쁜 예: {"error": "failed"}
좋은 예: {"error": "invalid_date_range", "message": "종료일은 시작일로부터 90일 이내여야 합니다. 입력값: start_date=2026-01-01, end_date=2026-06-01"}

좋은 에러 메시지의 조건: 무엇이 잘못되었는지, 어떻게 고치는지, 현재 입력값이 무엇인지가 담겨 있습니다. 모델은 이 메시지를 읽고 스스로 인자를 고쳐 다시 시도할 수 있습니다.

## 예제: 도구 설명 개선하기

다음은 실제 리뷰에서 자주 보이는 개선 사례입니다.

변경 전:
"search_docs: 문서를 검색합니다. query를 입력하세요."

변경 후:
"search_docs: 사내 기술 문서에서 관련 문서를 검색합니다. 에러 메시지나 기능 이름으로 검색할 때 사용하세요. 코드 예제가 필요하면 search_code를 쓰세요. query는 2~5개의 핵심 키워드로 입력하세요."

무엇이 달라졌나요. 용도가 구체화되었고, 쓰지 말아야 할 경우가 명시되었고, 입력 형식 가이드가 생겼습니다.

## 실습: 도구 3종 설계하기

가상의 "회의실 예약 시스템"을 위한 도구 3개를 설계해 봅니다.

1. 빈 회의실 조회
2. 회의실 예약
3. 예약 취소

각 도구에 대해 이름, 설명(언제 쓰고 언제 쓰지 말지 포함), JSON Schema 파라미터, 에러 메시지 예시를 작성합니다. 작성한 뒤에는 서로의 설명을 바꿔 읽으며 "이 설명만 보고 도구를 고를 수 있는가"를 점검합니다.

확인 문제

1. 좋은 도구 설명의 4가지 조건을 나열해 보세요.
2. required와 enum을 쓰는 이유를 각각 설명해 보세요.
3. 도구를 너무 잘게 나누었을 때의 문제 두 가지를 들어보세요.
4. 좋은 에러 메시지의 3가지 요소를 설명해 보세요.
