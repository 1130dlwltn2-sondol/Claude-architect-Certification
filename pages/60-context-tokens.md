# 60. 컨텍스트 윈도우와 토큰 경제학

Part 6에서는 시험 비중 15%의 Domain 5를 다룹니다. 비중은 가장 작지만, 에이전트 설계의 성패를 가르는 주제입니다.

## 토큰이란

모델은 텍스트를 토큰(token)이라는 단위로 나눠 처리합니다. 영어 단어 하나가 보통 1~2토큰, 한글은 글자당 2~4토큰 정도가 됩니다. 정확한 개수는 토큰나이저에 따라 다릅니다.

토큰을 세는 것이 중요한 이유는 비용과 직결되기 때문입니다. API 요금은 입력 토큰과 출력 토큰의 사용량으로 계산됩니다. 출력 토큰이 입력보다 비싼 것이 일반적입니다.

대략적인 감각:

- 짧은 대화 한 번: 수백 토큰
- 긴 문서 하나: 수만 토큰
- 코드베이스 전체: 수십만 토큰 이상

## 컨텍스트 윈도우

컨텍스트 윈도우(context window)는 모델이 한 번에 볼 수 있는 토큰의 최대량입니다. Claude의 최신 모델들은 20만 토큰 안팎의 넉넉한 윈도우를 제공합니다.

하지만 "넣을 수 있다"와 "잘 쓴다"는 다릅니다. 윈도우가 크다고 해서 무조건 많이 넣는 것은 좋지 않습니다.

- 비용: 입력 토큰이 늘어날수록 매 호출 비용이 증가합니다
- 주의력 분산: 관련 없는 정보가 많으면 중요한 정보를 놓칠 수 있습니다
- 속도: 입력이 길어지면 응답까지 시간이 늘어납니다

시험에서는 "컨텍스트 윈도우가 크니까 다 넣으면 된다"는 보기가 오답으로 나옵니다.

## 토큰 경제학

에이전트 설계는 토큰 예산 짜기입니다. 한 번의 작업에 쓸 수 있는 토큰이 정해져 있다고 생각하세요.

예산의 구성:

- 시스템 프롬프트: 고정 비용
- 컨텍스트(문서, 대화 기록): 가변 비용, 여기서 절감이 일어납니다
- 도구 정의: 도구가 많아질수록 고정 비용 증가
- 출력: 작업마다 다름

비용을 줄이는 방향:

1. 꼭 필요한 정보만 넣는다 (선택)
2. 긴 내용은 요약해서 넣는다 (압축)
3. 반복되는 내용은 캐싱한다 (재사용)
4. 작은 모델로 충분한 단계는 작은 모델을 쓴다 (분리)

4번은 20장의 라우팅 패턴과 연결됩니다. 쉬운 분류 작업에 큰 모델을 쓰는 것은 낭비입니다.

## 예제: 토큰 예산 계산

가상의 고객 지원 에이전트 한 건 처리:

- 시스템 프롬프트: 500토큰 (캐싱 가능)
- 고객 문의: 200토큰
- 관련 문서 3건: 6,000토큰
- 도구 정의: 800토큰
- 모델 출력: 400토큰

합계 약 7,900토큰. 하루 1,000건을 처리하면 약 790만 토큰입니다. 여기서 문서를 3건에서 1건으로 줄이면(관련도 필터링), 건당 4,000토큰 가까이 절감됩니다. 월 단위로 보면 큰 금액입니다.

이 계산을 손으로 해보는 것이 토큰 경제학의 기본기입니다.

## 실습: 내 프롬프트의 토큰 세기

Anthropic API의 토큰 계산 기능을 써서 다음을 측정합니다.

1. 평소 쓰는 긴 프롬프트의 토큰 수
2. 거기서 빼도 되는 부분을 지운 뒤의 토큰 수
3. 한글과 영어의 토큰 효율 차이 (같은 내용을 두 언어로)

3번은 흥미로운 발견을 줍니다. 같은 의미라도 언어에 따라 토큰 수가 다릅니다.

확인 문제

1. "컨텍스트 윈도우가 크면 정보를 다 넣는 것이 좋다"가 틀린 이유 3가지를 말해 보세요.
2. 토큰 예산의 4가지 구성 요소를 나열해 보세요.
3. 출력 토큰이 입력 토큰보다 비싼 것이 일반적인 이유를 추론해 보세요.
4. 위 예제에서 문서 3건을 1건으로 줄이는 것의 월간 효과를 계산해 보세요.
